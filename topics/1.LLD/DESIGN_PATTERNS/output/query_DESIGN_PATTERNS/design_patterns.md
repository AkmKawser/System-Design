# Software Design Patterns & Anti-Patterns Guide

Design patterns are formalized, reusable solutions to recurring problems in software engineering. When used incorrectly, overused, or misapplied, they can evolve into architectural **anti-patterns** and **inefficient implementations** that harm maintainability, performance, and testability.

This document classifies design patterns into their primary categories:
1. **Creational Patterns** (Object creation mechanisms)
2. **Structural Patterns** (Class & object composition)
3. **Behavioral Patterns** (Algorithms & assignment of responsibilities between objects)
4. **Concurrency / Architectural Patterns** (Multithreading & system-level organization)

---

## 1. Creational Patterns

Creational patterns abstract the instantiation process, decoupling a system from how its objects are created, composed, and represented.

| Pattern | Intent / Core Mechanism | Common Anti-Patterns / Misuse | Inefficient Design & Implementation Traps |
| :--- | :--- | :--- | :--- |
| **Singleton** | Ensures a class has only one instance and provides a global point of access to it. | **Global State & Hidden Dependencies**: Becomes an untestable global variable disguised as an object.<br>**God Object / Kitchen Sink**: The singleton slowly absorbs unrelated domain responsibilities.<br>**Concurrency Bottleneck**: Locks on shared singleton instances cause contention and race conditions. | **Synchronized Method Bottleneck**: Synchronizing the entire `getInstance()` method on every call rather than using Double-Checked Locking with `volatile` or Bill Pugh Holder.<br>**Reflection & Serialization Vulnerability**: Failing to guard constructors against reflection or missing `readResolve()`, resulting in duplicate instances. |
| **Factory Method** | Defines an interface for creating an object, but lets subclasses decide which class to instantiate. | **Poltergeist Factory**: Factories with no complex logic that simply do `return new Foo()`.<br>**Parallel Class Hierarchies**: Adding a new product requires creating a matching factory subclass every single time. | **Monster Switch-Case (Static Factory)**: Hardcoding a monolithic, 50-branch `switch(type)` in a static method instead of using dynamic registration or polymorphism, violating OCP.<br>**Reflection Overuse**: Calling `Class.forName()` on every instantiation inside the factory, causing heavy runtime overhead. |
| **Abstract Factory** | Provides an interface for creating families of related or dependent objects without specifying concrete classes. | **Factory Factory / Over-Engineering**: Nesting factories inside factories creating rigid, boilerplate-heavy class trees.<br>**Leaky Abstractions**: Generic product interfaces failing to expose family-specific functionality. | **Partial Instantiation**: Instantiating products across incompatible families because the factory allows ad-hoc overrides.<br>**Rigid Interface Bloat**: Modifying the abstract factory interface every time a new product type is introduced, forcing rewrites in all concrete factory classes. |
| **Builder** | Separates construction of a complex object from its representation, enabling step-by-step creation. | **Telescoping Builder**: Endless chained setter methods where default values or simple configuration records/DTOs would suffice.<br>**Incomplete / Inconsistent State**: Instances accessed before calling `build()`, or builder lacking terminal validation. | **Mutable Leaked Reference**: Passing mutable collections/objects directly through builder methods without defensive copying.<br>**Thread-Unsafe Shared Builder**: Reusing a single builder instance concurrently across multiple worker threads to construct different objects. |
| **Prototype** | Specifies the kinds of objects to create using a prototypical instance, creating new objects by cloning. | **Shallow Copy Bug**: Cloning objects containing mutable references, corrupting state across copies.<br>**Circular Reference Lock**: Deep copy implementations encountering circular references leading to stack overflow. | **Serialization-Based Cloning**: Implementing cloning via heavy Java/JSON serialization and deserialization, causing severe CPU and memory allocation penalties.<br>**Complex Object Graph Traversal**: Manual deep-cloning logic that recursively duplicates static or immutable lookup data unnecessarily. |
| **Object Pool** | Reuses objects from a pre-allocated pool instead of instantiating and destroying them on demand. | **Memory Leaks / Zombie Objects**: Borrowed objects not returned to the pool, or returned with dirty state.<br>**Premature Optimization**: Pooling cheap, short-lived objects that modern garbage collectors handle more efficiently. | **Coarse-Grained Synchronization**: Locking the entire pool queue on every checkout/checkin instead of using lock-free data structures like `ConcurrentLinkedQueue`.<br>**Unbounded Pool Growth**: Allowing the pool to grow infinitely without a maximum cap or eviction/idle cleanup policy. |

## 2. Structural Patterns

Structural patterns deal with object and class composition, using inheritance and interfaces to compose larger structures out of flexible components.

| Pattern | Intent / Core Mechanism | Common Anti-Patterns / Misuse | Inefficient Design & Implementation Traps |
| :--- | :--- | :--- | :--- |
| **Adapter** (Wrapper) | Converts the interface of a class into another interface clients expect, enabling incompatible interfaces to collaborate. | **Two-Way Adapter Spaghetti**: Overly complex bidirectional translations leading to unpredictable state mutations.<br>**Adapter Overload**: Wrapping trivial APIs with thin layers that obscure native errors and add indirection. | **Data Re-Serialization Overhead**: Converting complex data structures into intermediate JSON/XML strings back and forth just to fit an adapted method signature.<br>**Eager Full-Object Conversion**: Converting entire large relational entity graphs when the target client interface only requires two primitive fields. |
| **Bridge** | Decouples an abstraction from its implementation so that the two can vary independently. | **Over-Abstraction**: Splitting hierarchies that have no realistic future variation, increasing cognitive load.<br>**Explosion of Small Interfaces**: Fragmenting simple designs into excessive layers of abstraction without clear bounds. | **Excessive Dynamic Delegation**: Adding multiple intermediary bridge hops for performance-critical inner loops where direct composition or polymorphism suffices.<br>**Tight Coupling to Concrete Implementors**: Abstraction inadvertently exposing implementation-specific method arguments, defeating the decoupling. |
| **Composite** | Composes objects into tree structures to represent part-whole hierarchies, treating individual objects and compositions uniformly. | **Type Safety Violation**: Exposing child management methods (`add()`, `remove()`) on leaf nodes, leading to runtime unsupported-operation exceptions.<br>**Deep Recursive Traversal**: Naive traversals causing stack overflow or severe performance degradation on large hierarchies. | **Redundant Re-Calculations**: Calculating aggregated tree metrics (e.g., total price, total size) from scratch via full tree recursion on every read instead of caching with dirty flags.<br>**Parent Pointer Cycles**: Storing circular bi-directional references without weak references, preventing garbage collection. |
| **Decorator** | Attaches additional responsibilities to an object dynamically as an alternative to subclassing. | **Decorator Hell / Russian Doll**: Stacking 10+ layers of decorators, making debugging and stack trace analysis nearly impossible.<br>**Order Dependency**: Behavior silently breaks if decorators are wrapped in the incorrect sequence. | **Layered Overhead in Hot Loops**: Stacking multiple decorators around fine-grained, high-frequency method calls, leading to high call stack overhead.<br>**Subverting Core Contract**: A decorator silently swallowing exceptions or altering return values expected by the original component interface. |
| **Facade** | Provides a unified, simplified interface to a complex subsystem or library. | **God Facade**: Facade expands into a monolithic module that knows too much about internal subsystems.<br>**Walled Garden**: Facade completely prevents clients from accessing necessary lower-level functionality when special cases arise. | **Synchronous Request Chaining**: Facade executing multiple independent subsystem network calls sequentially instead of dispatching them in parallel via async futures.<br>**Leaky Subsystem Errors**: Allowing raw low-level SQL or socket exceptions to escape unmapped across the facade boundary. |
| **Flyweight** | Shares fine-grained object instances to support large quantities of objects efficiently with minimal memory. | **Leaky Extrinsic State**: Failing to strictly decouple intrinsic (shared) state from extrinsic (context-specific) state, causing data corruption across threads.<br>**Thread Synchronization Bottlenecks**: Heavy locking overhead on the shared flyweight factory cancelling out memory savings. | **Over-Granular Keys**: Using huge or expensive composite objects as cache keys in the flyweight factory, where hashing and lookup cost exceeds object instantiation.<br>**Unbounded Flyweight Cache**: Caching flyweights indefinitely without cache eviction (LRU / WeakReferences), leading to slow memory growth. |
| **Proxy** | Provides a surrogate or placeholder for another object to control access, delay initialization, or provide remote communication. | **Ghost Operations / Hidden Latency**: Virtual proxies triggering expensive I/O operations transparently during simple getter calls.<br>**Broken Identity (Self-Invocation Issue)**: Calling methods internally within a proxied object bypasses proxy interceptors (common in Spring `@Transactional` pitfalls). | **N+1 Remote Queries**: Lazy-loading virtual proxies firing individual network queries per object inside a loop instead of batch fetching.<br>**Heavy Reflection Dynamic Proxies**: Generating new dynamic proxy classes repeatedly on the fly instead of caching proxy bytecode. |

## 3. Behavioral Patterns

Behavioral patterns focus on algorithms, responsibility assignments, and communication mechanisms between interacting objects.

| Pattern | Intent / Core Mechanism | Common Anti-Patterns / Misuse | Inefficient Design & Implementation Traps |
| :--- | :--- | :--- | :--- |
| **Chain of Responsibility** | Passes requests along a chain of handlers until one of them processes the request. | **Black Hole Request**: Request travels through the entire chain unhandled and is silently dropped with no fallback.<br>**Hidden Cycles**: Misconfigured chain references creating an infinite loop at runtime. | **Deep Linear Scanning**: Traversing a long, un-indexed chain of 50+ handlers for every incoming request instead of using a hash-indexed dispatch table.<br>**Stateful Handlers Under Concurrency**: Storing request-specific mutable state in handler member variables, causing data corruption under multithreading. |
| **Command** | Encapsulates a request as an object, allowing parameterization, queuing, logging, and undoable operations. | **Class Explosion**: Generating a standalone command class for every trivial single-line action.<br>**Stale Command State**: Cached command objects holding references to outdated or mutated domain models during undo/redo operations. | **Fat Command Snapshots**: Storing entire application state snapshots inside command history stacks for undo functionality instead of storing precise delta operations.<br>**Unbounded Undo Stack**: Retaining unlimited historical command instances in memory without a circular buffer or depth limit. |
| **Interpreter** | Given a language, defines a representation for its grammar along with an interpreter that uses the representation to evaluate sentences. | **Grammar Bloat**: Using tree-based interpretation for complex languages instead of parser generators or AST compilers, destroying performance.<br>**Unbounded Recursion**: Deep syntax trees leading to call stack exhaustion. | **Re-Parsing Expressions**: Lexing and parsing the same static expression string repeatedly on every evaluation instead of compiling and caching the AST.<br>**Excessive Node Objects**: Instantiating thousands of small terminal and non-terminal expression objects for simple mathematical formulas. |
| **Iterator** | Provides a way to access the elements of an aggregate object sequentially without exposing its underlying representation. | **Concurrent Modification Hell**: Modifying an underlying collection during traversal without proper synchronized snapshots or concurrent iterators.<br>**Dual Traversal Inefficiency**: Iterators holding lock states over distributed or remote data stores. | **Eager In-Memory Buffering**: Fetching an entire million-row database result set into an in-memory list before returning an iterator instead of streaming rows.<br>**Iterating to Index**: Using sequential iterators to look up items by index repeatedly (`O(N^2)` aggregate traversal). |
| **Mediator** | Defines an object that encapsulates how a set of objects interact, preventing them from referring to each other explicitly. | **God Mediator**: Central mediator turns into a complex monolithic brain that knows every detail about every participant.<br>**Tight Coupling to Mediator**: Colleague objects become useless outside the context of that specific mediator. | **Synchronous Blocking Fan-Out**: Mediator invoking all colleagues sequentially on the caller thread, allowing one slow colleague to stall the entire system.<br>**Broadcast Flood**: Mediator notifying all registered colleagues regardless of message interest, causing massive CPU waste in filtering. |
| **Memento** | Captures and externalizes an object’s internal state without violating encapsulation, allowing restoration later. | **Memory Hog**: Storing full object snapshots frequently instead of delta states, leading to out-of-memory errors.<br>**Encapsulation Breach**: Exposing private state fields via public memento getters. | **Deep Cloning on Every Mutation**: Triggering a full deep clone of an entire entity hierarchy for every minor property change.<br>**Leaking Mutable References**: Returning internal mutable state objects directly from the memento without defensive copying. |
| **Observer** (Pub/Sub) | Defines a one-to-many dependency so that when one object changes state, all its dependents are notified and updated automatically. | **Lapsed Listener (Memory Leak)**: Subscribers fail to unsubscribe, causing the subject to retain strong references and preventing garbage collection.<br>**Cascade / Ripple Effects**: Notification storms and cyclic updates where Observer A updates Subject B, which triggers Observer A again. | **Synchronous Notification Blocking**: Iterating through hundreds of listeners synchronously, allowing one hanging listener to block the subject thread.<br>**Pushing Massive Payloads**: Pushing huge domain state objects to all subscribers when most observers only need a simple boolean event flag. |
| **State** | Allows an object to alter its behavior when its internal state changes, appearing to change its class. | **Combinatorial Explosion of States**: Defining separate classes for minor state nuances instead of composite state machines.<br>**Leaky Transitions**: State classes knowing concrete downstream states, creating tight circular coupling between states. | **Frequent Heap Allocations**: Instantiating a new state object on every single transition instead of caching and sharing stateless flyweight state instances.<br>**Incomplete Method Implementations**: Forcing state classes to implement 20 interface methods, resulting in dozens of empty or unsupported methods. |
| **Strategy** | Defines a family of algorithms, encapsulates each one, and makes them interchangeable at runtime. | **Strategy Creep**: Creating micro-strategies for 2-line functions that could simply be passed as lambdas / first-class functions.<br>**Context Pollution**: Strategy requiring broad context access, forcing the context to expose internal private variables. | **Per-Call Instantiation**: Instantiating a new strategy class inside a high-throughput loop instead of injecting a reusable singleton strategy.<br>**Excessive Context Pulling**: Strategy repeatedly querying the context object across method boundaries for data it could have received upfront. |
| **Template Method** | Defines the skeleton of an algorithm in an operation, deferring some steps to subclasses without changing algorithm structure. | **Fragile Base Class**: Subclasses inadvertently break the template algorithm flow by failing to call `super` or violating base invariants.<br>**Inheritance Rigidity**: Forced inheritance prevents classes from using alternative algorithms at runtime. | **Massive Skeleton Methods**: Writing 500-line base template methods with dozens of tiny abstract hooks, creating an unnavigable inheritance maze.<br>**Synchronous Tight-Loop Hooks**: Calling multiple empty hook methods inside high-frequency loops where JIT inlining fails to eliminate overhead. |
| **Visitor** | Represents an operation to be performed on elements of an object structure, letting you define new operations without changing element classes. | **Double Dispatch Complexity**: Adding a new element type requires modifying every single visitor implementation in the codebase.<br>**Encapsulation Breakdown**: Elements forced to expose their internal implementation details publicly so visitors can operate on them. | **Visitor State Accumulation**: Accumulating huge in-memory collections inside the visitor during deep tree traversals, causing GC pressure.<br>**Inefficient Dispatch Overhead**: Relying on double-dispatch recursion in performance-critical flat collections where simple switch/pattern matching is 10x faster. |

## 4. Concurrency & Architectural Patterns

| Pattern | Intent / Core Mechanism | Common Anti-Patterns / Misuse | Inefficient Design & Implementation Traps |
| :--- | :--- | :--- | :--- |
| **Active Object** | Decouples method execution from method invocation for objects that reside in their own thread of control. | **Queue Starvation & OOM**: Unbounded request queues running out of memory under burst traffic.<br>**Priority Inversion**: High-priority tasks stuck behind slow tasks in FIFO execution queues. | **Thread per Active Object**: Allocating a dedicated native OS thread per active object instead of backing them with a shared thread pool or virtual threads.<br>**Synchronous Future Blocking**: Client threads immediately calling `.get()` on the returned future, defeating asynchronous decoupling. |
| **Circuit Breaker** | Prevents an application from repeatedly trying to execute an operation that's likely to fail. | **Premature Opening / Flapping**: Setting trip thresholds too low, causing transient blips to shut down traffic.<br>**Infinite Half-Open Loop**: Poor probe requests that always succeed while real payloads consistently fail. | **Lock Contention on Metrics**: Using heavy synchronized blocks to track success/failure rates across threads instead of lock-free sliding window accumulators.<br>**Hardcoded Static Sleep**: Using static `Thread.sleep()` intervals for half-open transitions instead of exponential backoff with jitter. |
| **Read-Write Lock** | Allows concurrent read access while restricting write access to exclusive locks. | **Writer Starvation**: Continuous influx of readers preventing write operations from acquiring the lock.<br>**Lock Convoy**: High lock contention degrading throughput below single-thread performance. | **Using RWLock for Short Operations**: Using `ReentrantReadWriteLock` for quick in-memory reads where lock acquisition overhead exceeds `volatile` reads or `StampedLock`.<br>**Holding Lock Across I/O**: Retaining the read or write lock during slow network or disk I/O operations, blocking all other worker threads. |
| **Producer-Consumer** | Decouples producers of work from consumers through a synchronized shared queue. | **Unbounded Buffer Overflow**: Producers outpacing consumers, leading to system crash.<br>**Poison Pill Failure**: Malformed tasks persistently failing and blocking downstream consumers. | **Busy-Waiting / Polling Loops**: Consumers using non-blocking `poll()` in a tight loop with no backoff instead of blocking `take()` or event listeners.<br>**Single Lock Bottleneck**: Using a single mutex lock for both enqueue and dequeue operations instead of dual-lock queues (like `LinkedBlockingQueue`). |

## Summary: The "Golden Rules" to Avoid Pattern Abuse

1. **Rule of Three**: Do not introduce a pattern before a problem has surfaced at least three distinct times in your system.
2. **Prefer Composition Over Inheritance**: Patterns like Strategy and Decorator are safer long-term than rigid inheritance structures like Template Method.
3. **Beware Pattern-Driven Development (PDD)**: Patterns are tools to solve specific problems, not badges of design superiority. Favor simplicity (KISS / YAGNI) first.
4. **Benchmark Before Abstraction**: Indirection introduced by proxies, decorators, and dynamic factories has runtime costs. Never wrap high-frequency hot loops without profiling.
